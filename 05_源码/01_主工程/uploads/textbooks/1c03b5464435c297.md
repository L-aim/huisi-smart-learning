# 软件需求分析与建模 · 讲义一：需求获取与用例建模

> **材料性质声明**：本讲义为参赛作品自编教学材料，依据 UML 2.5 规范与软件工程通行的需求工程知识结构整理，**不是任何原版教材的翻版或摘录**。文中的例子（教务选课、图书馆借阅）为教学示例，非真实项目文档。

## 一、需求工程在做什么

软件出问题，多数不是"写不出来"，而是"写错了"。需求工程就是把"用户想要什么"变成"开发能照着做、验收能照着查"的过程，包含四步：

1. **需求获取（Elicitation）**：从涉众口中和现有材料里挖出真实诉求。
2. **需求分析（Analysis）**：判冲突、排优先级、划边界、建模型。
3. **需求规约（Specification）**：写成可评审的需求文档或用户故事。
4. **需求验证（Validation）**：确认写下来的确实是用户要的，且彼此不矛盾。

建模（尤其是 UML 用例图）主要发生在第 2 步：把自然语言诉求转成图形化、可讨论的结构。

## 二、需求获取的五种手段

| 手段 | 适用场景 | 主要风险 |
| --- | --- | --- |
| 访谈 | 涉众少、领域知识在个别人脑子里 | 受访者说"我以为你要的"，遗漏隐性需求 |
| 问卷 | 涉众多、要统计共性与优先级 | 问题设计有诱导性，答非所问 |
| 观察（现场跟岗） | 业务流程复杂、当事人说不清自己怎么做 | 被观察者改变行为（霍桑效应） |
| 文档分析 | 有旧系统文档、制度文件、表单 | 文档过时，与现状不一致 |
| 原型 | 界面类、交互类需求 | 用户看到界面就以为"快做完了" |

访谈的三个实用要点：

- **问流程不问功能**："这门课选课那天，你从打开系统到确认成功，中间做了哪些动作？"比"你需要什么功能"有效得多。
- **要例外不要只问正常路径**："什么时候会选不上？选不上之后学生怎么办？"——例外分支往往才是真正的需求难点。
- **复述确认**：把对方说的用一句话复述回去，"所以你的意思是容量满了要排队而不是直接拒绝，对吗？"，能拦下大量误解。

## 三、需求的分类

- **功能需求**：系统必须提供的动作与结果。例："学生可以选课，课程容量未满时选课成功。"
- **非功能需求**：质量与约束，常被漏掉却决定成败。例：并发 2000 人选课响应 2 秒内；成绩数据留存 5 年；支持 Chrome/Edge 近两个大版本。
- **约束**：不是系统属性而是外部给定条件。例：必须部署在校内网、必须复用统一身份认证。

常见错误是把非功能需求写成形容词（"要快""要好用"）——它必须可度量，否则无法验收。

## 四、用例图：参与者、用例、边界

### 4.1 参与者（Actor）

参与者是**与系统交互的外部角色**，不是具体的人，也不是系统内部的模块。识别参与者问三句话：

1. 谁使用系统的主要功能？
2. 谁需要系统主动提供信息（如定时报表的接收者）？
3. 系统要和哪些外部系统/设备交互（如统一身份认证、支付网关）？

判定要点：外部系统也算参与者；同一个人如果承担两种截然不同的职责（教师 vs 学生），应建成两个参与者；系统内部的定时任务不算参与者。

### 4.2 用例（Use Case）

用例是**参与者与系统之间一次完整的目标达成**，命名用"动词+名词"（选课、提交作业、申请补考），粒度是"参与者做完这件事就算成功"。

判定要点：用例不是界面、不是函数、不是步骤。把"点击保存按钮"当用例，就是把设计当成需求。

### 4.3 系统边界

矩形框表示系统边界，参与者画在框外，用例画在框内。边界画错的典型症状：把"数据库""消息队列"画成参与者——它们是内部实现。

## 五、用例之间的关系（本讲重点）

### 5.1 包含 include

**语义**：基础用例**每次执行都必须**执行被包含用例，被包含部分是多个用例共用的**必做片段**。

- 方向：基础用例 `----include----> 被包含用例`
- 例：`选课` include `校验容量`；`提交作业` include `校验截止时间`。
- 判定口诀：**"不做事就没法完成"** —— 去掉它，基础用例就不完整，所以是 include。

### 5.2 扩展 extend

**语义**：基础用例在**特定条件下、在扩展点**才执行扩展用例；扩展是**可选/例外**分支，基础用例本身仍然可以单独完成。

- 方向：扩展用例 `----extend----> 基础用例`（**箭头指向被扩展的基础用例**，这是最容易画反的地方）
- 例：`选课` 的扩展点"容量已满" ← `进入等待队列`；`借书` 的扩展点"有逾期未还" ← `缴纳滞纳金`。
- 判定口诀：**"没有它也能完成，有了它才处理例外"** —— 所以是 extend，且必须能指出扩展点。

### 5.3 include 与 extend 的四条对比

| 维度 | include | extend |
| --- | --- | --- |
| 是否必做 | 必做，每次执行 | 条件触发，可发生可不发生 |
| 方向 | 基础 → 被包含（箭头指向被包含） | 扩展 → 基础（箭头指向基础） |
| 是否有扩展点 | 无 | 必须有（写在基础用例里） |
| 典型场景 | 公共校验、公共登录检查 | 例外处理、可选增强功能 |

### 5.4 泛化（generalization）

用例之间、参与者之间都可以泛化，表示"是一种"。例：`支付` 泛化出 `微信支付`、`校园卡支付`；参与者 `校内用户` 泛化出 `学生`、`教师`。泛化不是 include/extend，别混用。

### 5.5 三个高频错误

1. **把可选分支建成独立用例却不标 extend**：需求描述里出现"如果……则……"，就该想到 extend 或备选流。
2. **箭头画反**：include 箭头指向被包含用例，extend 箭头指向基础用例。
3. **用 include 表达可选功能**："生成报表"不是每次"查询成绩"都必做，写成 include 就把可选强扭成必做。

## 六、用例描述模板

用例图说不清细节，必须配用例描述（用例规约）。最小可用模板：

```
用例名称：选课
参与者：学生（主）；教务系统（次）
前置条件：学生已登录且处于选课开放期
主流程：
  1. 学生提交课程编号
  2. 系统校验课程存在且在开放期
  3. 系统校验容量：未满则写入选课记录，返回"选课成功"
后置条件：选课记录存在，课程余量减 1
备选流：
  3a. 容量已满 → 进入等待队列，返回排队序号（对应 extend：进入等待队列）
  3b. 与已选课程时间冲突 → 提示冲突课程，不写入（对应 extend：冲突校验）
异常流：数据库写入失败 → 回滚并提示"稍后重试"
```

关键点：**主流程只写正常路径**，所有"如果"都放进备选流/异常流；每条备选流都应能对应用例图上的一个 extend 或一条独立用例。

## 七、从用例到可验收的需求

用例只交付"能做什么"，验收还需要可判定的标准：

1. 每个用例至少一条**验收标准**，写成"给定—当—则"：给定课程容量已满，当学生提交选课，则返回排队序号且不产生选课记录。
2. 非功能需求单独成表，逐条给出度量方式（响应时间、并发数、留存期、兼容范围）。
3. 需求之间做**冲突检查**：如"成绩即时可见"与"成绩需教师复核后发布"直接冲突，必须在需求阶段裁决，不能留到测试。

## 八、自测题

1. 判断关系：`提交作业` 与 `校验截止时间` 之间是 include 还是 extend？为什么？
2. 判断关系：`借书` 与"有逾期时缴纳滞纳金"之间是什么关系？箭头指向谁？
3. 找出错误：某小组把 `登录` 画成 include 到 `选课`、`退课`、`查成绩` 三个用例，另把 `打印成绩单` 也写成 include 到 `查成绩`。哪一处是错的，为什么？
4. 识别参与者：教务选课系统中，"统一身份认证服务""定时生成课表的后台任务""教学秘书"三者哪些是参与者？
5. 补验收标准：为"容量已满进入等待队列"写一条"给定—当—则"。

### 参考答案要点

1. include：每次提交作业都必须校验截止时间，属必做片段。
2. extend；箭头由"缴纳滞纳金"指向"借书"，扩展点为"存在逾期未还"。
3. `打印成绩单` 写成 include 是错的——查成绩时不必然打印，应为扩展或独立用例；登录被多个用例 include 是正确用法。
4. 统一身份认证服务是参与者（外部系统）；定时后台任务是系统内部功能，不是参与者；教学秘书是参与者。
5. 给定课程容量已满且学生不在队列中，当学生提交选课，则系统返回排队序号、不写入选课记录，余量保持不变。
