# 多 Agent 协作：答辩口径

> 用途：答辩/评审现场被追问「你们的多 Agent 到底是什么」时的标准回答。每条都指向一个可复现的证据，不靠形容词。

---

## 一、30 秒口述稿

> 我们的多 Agent 不是画一张图，而是**代码驱动的角色化编排真的开进程跑**。云端 v22 把九步编排的每一步放进独立子进程，一次回答里出现 **9 个互不相同的 pid**，跨步传值（薄弱点→检索词、阶段 ID→知识节点、题目 ID→提交）逐字段一致。落地前我们先把容器体检了一遍：`os.getpid()==1`、`fork` 起子进程 9ms、并发 7 个 fork 全部成功、`pids.max=max`——因为很多托管运行时是禁止 fork 的，不先证明能开进程，多进程就只是 PPT。我们也不掩饰边界：它是**同一容器内的多进程**，不是多个托管运行时实例。

---

## 二、核心主张（三句）

1. **角色是真的**：7 个角色（controller / profile / knowledge / path / diagnose / update / review）——不是提示词里的「你现在是 XX 专家」，而是各自独立进程 + 明确工具权限 + 明确交接数据结构。
2. **协作是真的**：跨角色不靠模型转述，靠 `StepRecord` 的字段级绑定——下游从上游返回值里按名字取值，取不到就 `MISSING_HANDOFF_DATA` 中止，而不是让模型「记得大概」。
3. **证据是真的**：每次运行都打印 pid 表与传值表；同一输入重复跑，工具名顺序与入参逐字一致，唯一差异是数据层自增的 ID。

## 三、评委十问

### Q1：你们的多 Agent 是不是就起了几个名字？

不是。判据是**进程边界**：云端 v22 一次回答里 `pid=[11,12,13,14,15,16,17,18,19]`，主控 pid 与之全不相同；本地版 7 个角色进程 + 1 个主控，`test_multi_agent.py` 断言「至少 7 个不同 pid、diagnose 两步同 pid」。如果只是提示词角色扮演，pid 会完全一样。

### Q2：为什么要开进程？开线程不够吗？

这是**刻意的取舍**。角色隔离要真隔离：一个角色的工具异常不能污染另一个角色的上下文。Python 线程共享解释器状态（GIL 之外还有全局变量/日志/异常钩子），进程才是真边界。代价我们清楚：进程间只能传可序列化数据、启动有开销、调试更难——所以传输用队列 + 结构化 `StepRecord`，不做共享内存。

### Q3：子进程怎么还能调 MCP？会话不就丢了？

主控**先握 MCP 会话，再 fork**。fork 出来的子进程直接继承 `Mcp-Session-Id` 与连接上下文，所以子进程里调工具与主进程调工具结果一致。这一点我们专门做了对照实验：同一工具在父进程与子进程各调一次，返回的 `raw` 字符串**逐字相同**（5293 字符同长度同内容）。

### Q4：为什么不用平台原生的多智能体？

如实回答：AgentArts 这个版本没有暴露多智能体原语（SDK 全量检索 `handoff|subagent|multi-agent` 零命中）。所以在**平台能力内**做的是「单运行时 + 代码驱动角色编排」，在**平台能力外**补了「进程级隔离」这一层。我们不宣称做到了跨机器调度。

**补充（2026-10-17 控制台核实）**：平台「智能体管理」页确有 `单智能体 / 工作流 / 多智能体` 三个页签，即平台**有**画布式的多智能体编排能力。但那是一条独立通路（低码画布、平台托管），与本项目的「容器内多进程 + 确定性九步」不是同一件事，我们没有使用该页签，也不宣称等价。

### Q5：你们怎么知道容器允许开进程？

先体检再写代码。部署一个只认「多进程体检」四字的探针（不调模型）在容器里跑：`os.getpid()==1`（入口进程即容器 PID 1）、2 vCPU、aarch64、`Seccomp 0`、`CapEff 0`、`pids.max=max`；`fork` 子进程 9ms、并发 7 个 fork 7/7 成功且 pid 互不相同；`spawn` 2428ms、`forkserver` 4683ms（能用但慢一个数量级，所以选 fork）。

### Q6：9 个进程会不会把容器压垮？

不会，而且我们**不是并发开**：九步是顺序依赖（第 2 步要先拿到薄弱点，第 3 步才好检索），所以是「同一时刻最多 1 个活跃子进程」，9 个 pid 是同一次回答里先后出现的。实测整条编排的进程开销在百毫秒级，`pids.max=max` 远未触顶。

### Q7：靠什么判定「这一步失败」？

三层，缺一层就会撒谎：
1. **协议层**：MCP 返回 `isError`；
2. **信封层**：`{"content":[{"text":"<业务 JSON>"}]}` 要剥一层才能看到业务字段（不剥，工具看起来「都成功」）；
3. **业务层**：剥出来后 `ok=false` 仍算失败，且 `error` 是**嵌套**的 `{"ok":false,"error":{"code","message"}}`，只读顶层会渲染成 `None: None`——我们的 v20 就栽在这，v21 才把 `ROLE_NOT_FOUND` 打出来。

### Q8：和 LangGraph / AutoGen 有什么不同？

它们是「让模型自由决定下一步」的编排框架，我们这条链是**确定性**的：工具名、顺序、入参来源都由代码写死，模型只负责生成自然语言与少量判断。这是为了可复现与可验收（本地回归评测集 50 条、CI 4/4、九步重复性对比）。代价是灵活性，收益是「同一句话问两次，九步逐字一致」。

### Q9：怎么证明不是演示脚本演的？

三份可复现材料：`test_multi_agent.py`（假注册表，27 条断言，含异常隔离、业务 `ok=false`、缺上文数据）、`test_multi_agent_real.py`（真业务注册表 + 真演示数据，7 进程 9 步全绿）、云端 `-s mp-2` / `-s mp-3` 两次独立会话原文（9 进程 / 8 进程，因为第 0 步按设计跳过）。任一条都能被评委当场复跑。

### Q10：你们没做到什么？

三条，主动说：① 同一容器内多进程，不是多运行时实例，没有跨机器调度；② 没有进程级故障重启（子进程崩了整炉失败，靠 `stop_reason` 报原因）；③ 前端只到「构建通过 + 接口打通（TestClient 真发请求）」，浏览器里手动点按未逐屏验证。

## 六、不要说过头的三句话

1. **「资源是按画像定制的」** —— 不要说。实际情况是：资源**类型**按 `weaknesses[0]` 匹配（薄弱点「混淆用例图与需求访谈」→ 推练习题库 / 语音辅导 / 视频推荐），资源**内容**在无大模型 key 时来自本地模板；资源预览里显示的 `major: 软件工程` 是演示数据写死的字段，不是按画像生成的。
2. **「知识库检索是语义检索」** —— 不要说。目前是本地词袋余弦（按文档长度归一化），同义改写召回弱；平台侧 `ict-course-kb` 的命中测试另算（0.05–1.00 那个），两者不是同一套实现。
3. **「多 Agent 是云端 7 个运行时就绪」** —— 不要说。云端是**一个容器内 fork 出 7 个子进程**（实测 pid 11–19 互不相同）；平台并没有 7 个独立 AgentRuntime。
