# 作品分享帖：把学习闭环真正跑在云端 MCP 上

> 一句话：我们不只做了一个能回答问题的智能体，而是把「画像 → 路径 → 练习 → 评估 → 路径更新」这条闭环，跑通在华为云 AgentArts 托管的 MCP 运行时上，并把过程中每一个「以为通了其实没通」的坑都留了证据。

---

## 一、解决什么问题

求职/学习类智能体最常见的失败不是「答不出来」，而是**答得很像样、但底层其实没执行**：

- 工具列表里明明有 9 个工具，模型说「工具里没有这个接口」；
- 三道题全答对，系统判定全错；
- 提交成功并返回了掌握度 33，下一次查询变成 0。

这三种现象我们全都真遇到过，而且全都定位到了根因。这篇分享就围绕「怎么把『看起来通了』变成『确实通了』」展开。

## 二、技术方案

```
Vue 3 前端 ──► 后端 FastAPI ──► 业务服务（画像/路径/练习/评估）
                                      │
                                      ▼
                        AgentArts 托管 Agent（IAM 签名直连）
                                      │
                                      ▼
                        MCP 运行时（9 个工具，Streamable HTTP）
```

- **MCP 工具集**：`get_student_profile`、`get_role_competency`、`get_project_status`、`search_knowledge`、`get_exercise_session`、`submit_exercise_answer`、`get_wrong_book`、`get_learning_evaluation`、`add_learning_branch`。
- **加固层**：新增 `mcp_server/hardening.py`，纯 ASGI 中间件提供 API Key 鉴权、滑动窗口限流、日志脱敏、`/healthz` 健康检查，四条机制**默认非阻断**（云端走 IAM 签名、不带 Key，强校验会当场打断全部工具）。
- **可观测**：日志只记方法/路径/状态/耗时/客户端指纹，客户端标识用 `sha256(key)[:8]`，全链路无明文密钥。
- **多 Agent 编排**：确定性九步由代码驱动、不靠模型自由规划；云端 v22 把每一步放进独立子进程（9 步 = 9 个 pid），主控先握 MCP 会话再 fork，子进程继承 `Mcp-Session-Id`；本地无 fork 环境自动退回单进程。

## 三、七个值得说的排查故事

### 1. 工具上线 ≠ 能用：第二道门槛在提示词里

9 个工具注册成功、`TOOLS: 9` 确认无误，但问「错题本里有哪些题」，模型回答「工具里没有独立的错题本接口」，转而用画像里的 `corrections` 字段凑答案。

根因不在 MCP：`agent_iam.py` 的系统提示词里【可用工具】是**手写的三行清单**，只列了 3 个工具。模型据此认为自己没有新工具。

改法：把提示词扩到 9 个工具，并加「意图 → 工具」路由表，同时规定「工具返回 `ok=false` 时必须如实转述 `code` 与 `message`」。复测后「工具里没有这个接口」这句话消失，返回了只有 `get_wrong_book` 才有的字段。

### 2. 答对判错：字符串严格比较

三道题提交后全部判错，而表格里「你的作答 B / 参考答案 B」自相矛盾——模型自己都指出「判定结果与答案本身互相矛盾」。

根因：判题是严格字符串比较，而归一化函数只处理纯字母，**非纯字母原样返回**，于是 `"B. 参与者与用例之间的交互关系" != "B"`。

改法：在 MCP 工具层加 `_normalise_answer_input`，统一处理 `B` / `b` / `B. 选项全文` / `选项B：xxx` / `B、C` / `BC` / `["B","C"]`，返回里同时给出原始输入与归一化结果便于对账。复测 3/3 判对（修复前 3/3 判错）。

### 3. 写进去读不到：平台认的会话头不是 MCP 的那个

提交返回 `mastery: 33`，紧接着查状态读回 `0`；一轮内连提三题，`answered_count` 恒为 `1`。同一份代码在本机容器里却 7/7 通过。

排查到 MCP 协议层的 `Mcp-Session-Id` 复用**完全无效**，最后在 SDK 源码里翻到答案：

```python
# agentarts/sdk/runtime/model.py:11
SESSION_HEADER = "x-hw-agentarts-session-id"
```

平台是按这个头做容器亲和的，`mcp-session-id` 只影响 MCP 协议层握手。在客户端补上该头（取值与 invoke 的 `-s` 一致）后：一次 invoke 内 `mastery` 走出 `33 → 67 → 100`，阶段 `status=completed`、`next_stage_id=stage-2`，加分支也拿到了正确的 `parent=stage-1`。

**这条约束官方文档里不显眼，是从源码里挖出来的，我们认为是本作品最有价值的踩坑记录。**

### 4. 加固不能把功能打断

云端调用走 IAM 签名、不带 API Key，如果加固层做强校验，9 个工具会当场全废。所以四条机制全部默认非阻断，并加三道保险：未配 Key 就不鉴权、加固层异常自动降级回原生 `mcp.run()`、`MCP_TRANSPORT_DIRECT=1` 一键跳过。

本地用「限流压到 3 次/分」的方式验证六项，全部通过；其中日志脱敏的硬证据是：全文检索明文密钥，命中 **0** 行。

### 5. 记忆抽取默认是关的：写入成功、检索永远 0 条

平台记忆库建好、`add_messages` 返回 `ADD_OK`，看起来一切正常，但 `search_memories` 永远是 0 条——**不报错、不告警，是纯静默失败**。

根因：新建 Space 的 `memory_extract_enabled` 默认 `False`，不打开就只存原始消息、不抽取记忆条目，而检索只查抽取出来的条目。改法一行：

```python
update_space(space_id, memory_extract_enabled=True, memory_extract_idle_seconds=30)
```

改完后 45 秒再查：`SEARCH_TOTAL 4`、`LIST_MEMORIES 4`，两类策略都在产出（`semantic` 记原话 / `user_preference` 记归纳，含 `context` / `preference` / `categories`）。

验收方式刻意选了最硬的一条：新会话 `memory-2` 此前从未出现过的信息，却把 `memory-1` 里的自述（include / extend 混淆）按字段逐字复述出来，并声明「未调用任何工具」——会话历史为空，这条信息只能来自记忆库。

顺手记两个被证伪的方向：记忆**不按 `actor_id` 隔离**（三种过滤都返回 5 条），解析也没取错字段（`record.content` 就是字符串）。真相更朴素：模型那轮选了知识检索、没引用注入的记忆——**记忆注入是软约束**。

### 6. 多 Agent 不是画图：先在容器里体检能不能开进程，再写代码

「多 Agent」最容易变成一张 PPT——画几根箭头、标几个 Agent 名字。我们最初也只到「声明态」：6 个生成智能体各自声明所依赖的 MCP 工具，但编排还是单进程按角色顺序跑。要让它算得上多 Agent，就得真的多进程。

可托管运行时为了安全，普遍会禁止 fork。**所以第一步不是写编排，是在云端容器里先体检**——部署一个只认「多进程体检」四个字的探针（不调模型、零额外成本），让它在容器里自己跑：

- `os.getpid() == 1`：入口进程就是容器主进程；2 vCPU、aarch64、`Seccomp 0`、`CapEff 0`、`pids.max=max`
- `fork` 起子进程 **9ms**；并发 **7 个 fork 子进程 7/7 成功、pid 互不相同**
- `spawn` 2428ms、`forkserver` 4683ms —— 能用但慢一个数量级

结论是可以做。但上线 v20 第一次跑还是失败，报错只有一行 `None: None`。根因不在多进程：业务失败对象是**嵌套**的，`{"ok": false, "error": {"code": "...", "message": "..."}}`，我只读顶层 `code/message`，于是真实的 `ROLE_NOT_FOUND` 被渲染成 `None: None`。修完 v22 跑通：**9 步 = 9 个独立进程，pid 互不相同**，跨步传值（薄弱点→检索词、阶段 ID→知识节点、题目 ID→提交）逐字段一致。

还留了一个坑：`multiprocessing.Queue` 版 fork 子进程**退出码是 1**（spawn/forkserver 是 0），因为解释器收尾时 queue 的 feeder 线程先被 terminate。改法很朴素：子进程写完结果直接 `os._exit(0)`，跳过收尾。

### 7. 真正的 RAG 验收，是看它敢不敢说「资料里没有」

平台知识库建好后，我们没急着接智能体，先做命中测试——这一步很多人跳过，跳过就等于没建。四个查询里最值钱的不是满分那个，而是 **0.05 分那个**：

| 查询 | 最高分 | 命中内容 |
|---|---|---|
| 入门视频建议看多久 | **1.00** | 「难度：入门 / 建议时长：10-20 分钟」整段 |
| 连续答错三次怎么办 | **0.96** | 失败兜底「切换教师模式」 |
| include 和 extend 区别 | **0.05** | 「一、方案概述」——只是**提到**，没有讲解 |

由此得到两条硬事实：**平台服务端不做阈值过滤**（任何查询都返回全部 13 条，0.05 也在里面），阈值必须调用方自己卡；而 0.05 这条恰好是「资料里真没有」的负例——它和我们云端智能体 `search_knowledge` 那句「属于『提到』而非『讲解』」互相印证，两条独立通路给出同一结论。

于是提示词里专门写了一条：**检索结果与问题无关或匹配度很低时，直接说「现有资料里没有讲到这个点」，不要猜、不要补**。试运行第三问的回答就是「我在知识库中未检索到关于用例图中 include 与 extend 区别的相关内容」——模型明明自己讲得清，但被检索分值挡住了。

**这才是「知识接入」的证据**：不是能答出来，而是知道哪里不能答。

顺带记一条平台限制，免得别人重走：平台知识库**只服务平台内智能体**，SDK 里没有知识库模块、控制台也没有知识库地址或 API Key，所以高代码智能体调不到它；官方《第三方通用知识库接入规范》是让**你**实现检索接口给 AgentArts 调，方向是反的。

## 五、边界与未做（不粉饰）

- **多 Agent 是「同一容器内多进程」，不是多个托管运行时实例**：云端 v22 已按角色把 9 步拆成 9 个进程（主控先握 MCP 会话再 fork，子进程继承 `Mcp-Session-Id`），但进程共享一个容器、一个进程组，没有跨机器调度，也没有进程级故障重启；本地版是 7 个角色进程 + 主控，可单机复现。
- **知识检索未改向量**：我们做了对比实验，现有语料仅 2 篇时哈希向量 Recall@1 只有 0.50，低于词袋余弦的 1.00。**没有证据支持就改动**，所以不改，脚本留在仓库等语料扩充后复跑。
- **前端只到「构建通过 + 接口打通」**：已 `vue-tsc -b` 0 错误、`vite build` 通过（`dist/` 101 文件），编排页已接 `/orchestration/multi-agent/run` 并用 `TestClient` 真发请求打通过；但浏览器里手动点按整条交互流程未逐屏验证。
- **演示数据已标注**：登录凭据、课程目录、首页数据、写死的 `Lv. 4` 等 5 处均在前端展示层，清单见 `演示数据标注清单.md`，不参与后端判定。

## 七、一句话总结

**这条闭环的价值不在「能跑」，而在于我们能为每一段「它确实跑了」拿出证据，也能为每一段「它还没跑」明确说不。**
